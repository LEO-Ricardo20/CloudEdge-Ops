# 遥测可靠性验证

## 本版机制

设备每次启动生成 bootId，每条新采样递增 sequence。服务端按 deviceId + bootId + sequence 判断是否已经接收；相同身份但内容不同返回 409，避免静默覆盖。重复包返回原始采样，不刷新最近接收时间，避免重复旧包维持“在线”状态。

模拟器只有一条内存待确认消息，失败后保留原始 timestamp、metrics 和 reportedState，下个循环继续重试，确认后再采新数据。命令处理在遥测确认后运行。持续认证错误也会保留该消息并记录错误，需要修复配置；没有无限离线采样队列。

## 可复现故障矩阵

执行 `npm run test:reliability`。

| 场景 | 测试方法与期望 |
| --- | --- |
| 服务端提交后响应丢失 | 真实 HTTP 202 被测试发送器丢弃并抛错；原包重试只产生一条采样和一次告警创建 |
| 通信不可用 | 发送器连续抛错；恢复后发送内容和最初观测时间一致 |
| 服务端恢复 | 从真实 JSON 文件重新建立平台；重复包不写盘、不推送、不刷新在线时间 |
| 设备进程重启 | 真实模拟器重启后 bootId 改变，固件版本仍恢复一致 |
| 身份冲突 | 同一启动标识/序号改写指标，明确拒绝 |
| 去重窗口溢出 | 仅保留 240 个采样；窗口内重复被识别，窗口外旧序号可再次接收 |
| 存储故障 | 既有持久化测试验证内存回滚、主文件保留及备份恢复 |

## 明确限制

- 不保证断网期间每次采样均被保存：当前暂停新采样，只有一条待确认消息。
- 待确认消息不落盘，模拟器退出会丢失。旧消息返回的 duplicate 不刷新在线时间；下一条新采样才恢复在线。
- 去重不是无限历史索引；超过 240 条的重放可能再次接收。没有全局单调序号约束，不承诺对乱序新消息做状态保护。
- 这是 HTTP 模拟设备的故障注入验证，不是物理网络丢包率测试、MQTT QoS 测试或硬件断电测试。
- 未实现 ESP32、真实固件下载、签名、自检回滚、PostgreSQL 或生产规模验证。

## 简历表述建议

可以写“实现启动标识与序号驱动的有界遥测幂等处理，通过 HTTP 响应丢失、重复投递和重启恢复测试验证状态一致性”。不要写“实现零丢包、恰好一次投递、无限离线缓存或生产级 OTA”。
